# quagent のドキュメント構成・作成規約

quagent は、VM 境界とホスト側制御による強固な隔離機構、LLM/MCP プロキシ、DLP、Git PR 連携など多岐にわたる機能を備えています。機能追加や改修に伴ってドキュメントが肥大化・雑然化することを防ぎ、常に利用しやすく保守性の高い状態を維持するため、本書でドキュメントの体系・役割分担・記載基準を定めます。

ドキュメントの新規作成、更新、またはリファクタリングを行う際は、必ず本規約に従って適切なファイルに適切な粒度で記述してください。

---

## ドキュメント体系と配置場所

quagent のドキュメントは以下の 4 層に分離して管理します:

| 配置パス | ドキュメント種別 | 対象読者 | 主な役割 |
| --- | --- | --- | --- |
| `README.md` | 利用者ガイド・入門 | 一般利用者 / 導入者 | 基本的な使い方、クイックスタート、各機能の利用方法と設定例 |
| `docs/design.md` | アーキテクチャ・設計仕様 | 設計者 / セキュリティ監査者 / 開発者 | 内部アーキテクチャ、隔離の仕組み、脅威モデル、詳細仕様、今後の課題 |
| `docs/development.md` | 開発者ガイドライン | リポジトリの開発者 / コントリビューター | ビルド/テスト/CI 手順、リポジトリ構成、守るべき設計の原則、コミット/PR 規約 |
| `.opencode/skills/<名前>/SKILL.md` | AI エージェント向け手順・規約 | AI エージェント (OpenCode, agy 等) | 特定の保守・作業タスクに特化した詳細手順、遵守すべき規約 |

---

## 各ドキュメントの役割分担と記載基準

### 1. `README.md` (利用者ガイド)

**目的:** 初めて利用する人や日々の利用者が、迷わずセットアップして操作・設定できるようにする。

- **記載すべき内容:**
  - ツールの概要と主目的（1〜2 段落）
  - 主な特徴（箇条書きで簡潔に）
  - ホストに必要な環境・依存コマンド
  - ビルドとインストール手順（`make build`, `make install`）
  - 基本的な使い方（TUI 起動、CLI サブコマンド一覧、実行時 tmux の操作、再起動/終了）
  - 各機能の利用方法と代表的な設定例（JSON 設定、MCP ツール名、承認コンソールでの操作入力）
  - 関連ドキュメント（`docs/design.md`, `docs/development.md`）へのリンク
  - ライセンス
- **記載してはならない内容 (アンチパターン):**
  - **内部アーキテクチャやカーネルレベルの実装詳細:** 名前空間の多重化、cBPF seccomp の syscall 一覧、Landlock ABI、PID 検証ロジック、動的 CA 生成の暗号処理などは書かない（`docs/design.md` に書く）。
  - **多層防御の全容表や脅威モデル:** 詳細なセキュリティ層の一覧表は書かない（`docs/design.md` に集約し、README ではリンクで案内する）。
  - **今後の開発課題・ロードマップ:** 実装予定の課題リストは書かない（`docs/design.md` の「今後の課題」に書く）。
  - **開発・テスト手順:** `go test` や CI の説明は書かない（`docs/development.md` に書く）。
  - **長大なベタ書き段落:** 1 つの段落に画面遷移・内部動作・例外処理を詰め込まず、見出しや箇条書きで整理する。

### 2. `docs/design.md` (設計・脅威モデル・内部仕様)

**目的:** セキュリティモデル、多層防御アーキテクチャ、内部コンポーネント間の通信制御、脅威モデルを網羅的かつ正確に記録する。

- **記載すべき内容:**
  - 隔離の仕組み（QEMU プロセスサンドボックス、名前空間、Landlock、cBPF seccomp）
  - 通信経路（vsock のポート制御、CID 検証、nftables、自前 DNS、透過プロキシ、動的使い捨て CA）
  - VM 内部仕様（ベースイメージ、作業ユーザー、使い捨て overlay、`.tmp` 同期）
  - VM 内部の多層防御（PID 検証によるプロセス間権限分離、設定ファイル不可視化、Docker へのサンドボックス継承）
  - 多層防御の全体像（第 1 層〜第 6 層の硬化策一覧表）
  - 敵対的・暴走エージェントへの備え（リソース制限、DoS 対策、エスケープシーケンス無害化）
  - LLM 認証プロキシ、OpenAPI ツールサーバー、header_policy、Content Guard / DLP の内部仕様と挙動
  - PR 作成とコミットの再署名フロー（二重署名、fsck 検証）
  - アーキテクチャ上の今後の課題（未解決の設計課題、将来の堅牢化項目）

### 3. `docs/development.md` (開発者ガイドライン)

**目的:** quagent 本体のコードにコントリビュートする開発者が、設計原則を損なわずに品質の高いコード・テストを作成できるようにする。

- **記載すべき内容:**
  - ビルド・テスト・静的解析コマンド（`make build`, `make test`, `make vet`, `gofmt`）
  - CI ワークフローの概要と依存更新ポリシー（Dependabot）
  - リポジトリ構成（各パッケージの責務）
  - 守るべき設計の原則（「隔離の主体はホスト側に置く」「機密情報を VM に持ち込まない」等）
  - コミットメッセージ規約（接頭辞 `feat(...)`, `fix(...)`、日本語記述）
  - PR の作成方針
  - ドキュメントの配置と役割、利用可能なスキルへのリンク

### 4. `.opencode/skills/<名前>/SKILL.md` (エージェントスキル)

**目的:** AI エージェントが特定の作業（レシピ編集、ドキュメント整理など）を自律的に遂行する際の「手順書」「判断基準」を提供する。

- **運用中のスキル一覧:**
  - `recipe-authoring`: ベースイメージレシピ（`recipe.json`, `user-data.yaml`）の作成・修正規約
  - `document-authoring`: 本ドキュメント作成・整理規約
- **記載すべき内容:**
  - YAML frontmatter（`name`, `description`）
  - 作業時の前提条件、配置場所、命名規約
  - チェックリストおよび遵守すべきルール
  - 失敗しやすいポイントや注意点

## 機能追加・変更時のドキュメント更新ワークフロー

新機能の追加や仕様変更を行う際は、以下のフローでドキュメントを更新してください:

```
新機能の実装 / 変更
  │
  ├─ 1. docs/design.md を更新
  │     内部仕様、脅威モデル、多層防御表への反映、制限事項を記録
  │
  ├─ 2. README.md を更新 (必要最小限)
  │     ユーザーが使うための CLI オプション、config.json 設定例、操作方法のみ追記
  │     ※ 内部アーキテクチャや長文の説明を README に追加しないこと！
  │
  ├─ 3. docs/development.md を更新 (開発ルール・パッケージ追加時)
  │     新しいパッケージや設計原則に関わる変更があれば反映
  │
  └─ 4. 相互リンクと用語の整合性を確認
        リンク切れがないか、各ドキュメントで用語が統一されているか確認
```

## 記述スタイル・フォーマットの規約

1. **言語とトーン:**
   - 本文は丁寧な日本語（「〜します」「〜してください」の敬体）で記述します。
   - 専門用語（英語）は適切に併記または統一します（例: `名前空間 (namespace)`、`透過プロキシ`）。
2. **見出し構造:**
   - `#` はタイトルのみ（ファイル内に 1 つ）。
   - `##` を主要セクション、`###` をサブセクションとし、深すぎる階層（`####` 以上）はなるべく避けます。
3. **設定例・コード例:**
   - 設定例（JSON、YAML、シェル）には、主要なキーの説明やコメントを添えます。
   - 実際に動作する最小限の設定例を示し、過度に複雑な例は避けます。
4. **相互リンクの活用:**
   - 他のドキュメントに詳細がある場合は、積極的に相対パスでリンクします（例: `README.md` からであれば `[docs/design.md](docs/design.md)` や `[docs/development.md](docs/development.md)` の形式）。
