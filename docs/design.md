# 設計と脅威モデル

quagent は「隔離の主体はホスト側に置く」原則のもと、非特権名前空間、nftables、vsock 単一通信路、および VM 内部サンドボックスを組み合わせた多層防御アーキテクチャを採用します。

外部監査者および開発者向けに、内部アーキテクチャ、アクセス制御ロジック、脅威モデルの詳細仕様を規定します。基本的な利用方法は [README.md](../README.md)、開発規約は [development.md](development.md) を参照してください。

## 多層防御の全体像: ホスト境界制御を主軸に 6 層の硬化策で防衛する

quagent は境界制御と内部制限を組み合わせた多層防御を採用しています。

| 防御層 | 主な硬化策 |
| --- | --- |
| **第1層: ホスト & VM 境界** | ・QEMU (KVM) による完全隔離と非特権名前空間の分離<br>・QEMU プロセスのサンドボックス化（seccomp / Landlock / tmpfs）<br>・ホスト・VM 間通信の vsock 単一化（sshd 排除）<br>・ホスト側リソース監視と動的保護（容量検査、ACPI 停止） |
| **第2層: ゲストOS & サンドボックス** | ・非特権 `agent` ユーザーと rootless Docker<br>・カーネル硬化（Lockdown、モジュール署名、32bit ABI 廃止）<br>・VM 内コマンドの seccomp / Landlock 制限<br>・プロセス間権限分離（窓口 PID 検証、設定ファイル不可視化） |
| **第3層: ネットワーク & Egress 遮断** | ・ホスト側 nftables による Default Deny と IPv6 遮断<br>・自前 DNS による名前解決制御と内部向け IP 遮断<br>・Web 透過プロキシによる SNI / Host 検証<br>・Content Guard / DLP による機密情報漏洩遮断と動的緩和 |
| **第4層: 機密情報の非保持** | ・LLM API キー、GitHub トークン、GPG 鍵を VM に置かない<br>・ホスト側 LLM 認証プロキシ（推論・モデル一覧のみ転送）<br>・OpenAPI ツールサーバーのホスト側プロキシ<br>・使い捨て鍵とホスト正規鍵による二重署名 Git PR |
| **第5層: コントロール & 承認** | ・承認コンソールによる対話確認（通信申請、動的緩和、PR 作成）<br>・Git オブジェクト取り込み時の `transfer.fsckObjects` 検査<br>・画面偽装防止（制御文字・Bidi エスケープ）<br>・各種リソース上限と改変不能なホスト監査ログ (`host.log`) |
| **第6層: ビルド & サプライチェーン** | ・静的リンクバイナリ (`CGO_ENABLED=0`)<br>・ベースイメージの GPG 署名検証 (Arch, Gentoo)<br>・Dependabot 更新の 7 日間遅延適用 |

## 隔離の仕組み: 非特権名前空間と vsock 単一化で QEMU を封じ込める

QEMU は非特権な user/mount/net/pid/ipc/uts 名前空間の内部で動作します。ホスト側の全処理は非 root（非特権）ユーザーで実行されます。

ホスト上の QEMU プロセス自体に対しても、以下のサンドボックスを多層で適用します。

- **QEMU ネイティブ seccomp:** `-sandbox on,spawn=deny` 等を適用
- **ホスト側 cBPF seccomp:** 危険なカーネル攻撃システムコール 31 種の拒否、32bit/x32 ABI 偽装の強制終了
- **Landlock:** ファイル書き込み権限を作業ディレクトリおよび追加ディスクのみに限定
- **ホームディレクトリの保護:** Mount 名前空間内で必要な quagent ディレクトリ以外を tmpfs で不可視化
- **リソース制限:** コアダンプ無効化 (`RLIMIT_CORE = 0`)、FD 上限、プロセス数上限、プロセス優先度（nice 10 / OOM スコア 500）の調整

QEMU が外部へ確立しようとするソケット通信は、netns 内の nftables ルールを経由します。許可リストに登録されていない接続先への新規アウトバウンド通信はすべて拒否されます。ルールは VM の外部（ホスト側 netns）に存在するため、ゲスト OS 内の root 権限からも参照・改変できません。

ホスト側によるアクセス制御に加えて、VM 内部で実行されるコマンドに対してもエージェント自身では解除できない制限（seccomp / Landlock）を適用します。隔離の根幹は VM 境界およびホスト側の制御にあり、VM 内部の制限は危険なシステムコールの侵入経路を減らす追加の防御層として機能します。

```
host ── vsock ──────────────────────────────────────► guest (quagent __guest)
host ◄─ vsock (run ごとのポート、この VM の CID だけ) ◄─ guest 127.0.0.1:7070
                                                       (quagent.host: LLM / MCP)
        qemu ── tap0 ──► slirp4netns ──► host (uplink)
        └ 子 netns: nftables (許可した IP への TCP 80/443 以外を reject) + 自前 DNS
                     + Web の透過プロキシ (SNI/Host を許可名と照合。任意で TLS 終端してヘッダ制限)
```

ホストから VM の操作（コマンド実行、仮想端末、リポジトリ同期、PR 作成用の git fetch など）はすべて vsock 経由で行われます。通常のネットワークを経由しないため、nftables や DNS の影響を受けず、SSH も使用しません。VM 内部では quagent 自身が作業ユーザー権限で vsock 接続を待ち受けます。実行ごとに cloud-init の seed ISO でバイナリを持ち込むため、quagent を更新してもベースイメージを再ビルドする必要はありません。また、接続はホストからのもののみを受け付け、同時接続上限（64本）を設けています。

VM 内部で実行される一般コマンドに対しては、seccomp フィルタにより `AF_VSOCK` ソケットの作成自体を遮断しています。そのため、エージェントやビルドプロセスからホスト側 vsock の任意待受ポートへ直接接続・ポートスキャンすることはできません。ホスト側の LLM/MCP 窓口への通信は、`quagent.host:7070` 経由で常駐デーモン `quagent-guest` が中継します。

sshd は完全に停止・無効化されます。systemd-ssh-generator が生成する vsock / UNIX ソケットの sshd も含めてすべて mask され、停止していない場合は VM の起動を中断します。quagent の VM 操作はすべて vsock 経由で行われ、SSH 接続経路は一切存在しません。

## VM 内部仕様: 使い捨てスナップショットと非特権 agent ユーザー

- **ベースイメージ:** 各 OS のレシピからビルドされます。いずれのイメージも rootless Docker、opencode、Claude Code、agy、Codex を同梱しており、root 権限で動く Docker デーモンは動作させません。
- **作業ユーザー `agent`:** sudo 権限を持たない一般ユーザーです。作業ディレクトリは `/work` であり、ここに対象リポジトリを履歴ごとクローンし、ホストと同じブランチをチェックアウトします。同期されるのは現在チェックアウト中のブランチと origin のリモート追跡ブランチのみであり、他のローカルブランチやタグは持ち込みません。ブランチの先頭コミットは既定では upstream（fetch 済みのリモート先端）です。ローカルの未 push コミットを渡す場合は `--local-head`（TUI オプション）を指定します。未コミットの変更はいずれの場合も同期されません。
- **使い捨て環境:** VM は毎回ベースイメージの overlay スナップショットから起動され、終了時に破棄されます。対話セッション終了時に TUI でエージェントを選び直して再起動する場合は、VM を破棄せず、エージェントの設定のみを差し替えます。終了を選んだときはホスト側のログを残さない選択も可能です。残存した作業ディレクトリは次回起動時に自動クリーンアップされます。
- **仮想化支援 (KVM):** VM には CPU の仮想化支援機能（svm / vmx）を公開しないため、VM 内部では KVM を使用できません。VM 内部でさらに VM を実行する場合（quagent 本体の開発など）は `--nested-virt`（TUI オプション）を指定します。
- **`.tmp` ディレクトリの同期 (`--mount-tmp`):** ホスト側の `<repo>/.tmp` と VM 内の `/work/.tmp` を相互同期します。VM 内の `/work/.tmp` は専用の独立した仮想ディスク（64 MiB、noexec マウント）であり、ホスト側のディレクトリを直接マウントしません。起動時にホスト側 `.tmp` の通常ファイル（合計 32 MiB まで）を VM へコピーし、終了時に VM 内の内容をホスト側へ回収します。回収対象は通常ファイル（パーミッション 0644）とディレクトリのみです。シンボリックリンクや実行権限はホスト側に作成されません。
- **共通スキルの配置 (`skills_dir`):** ホスト側の共通スキル（既定: `~/.config/quagent/skills`）を起動時に vsock 経由で VM 内の `~/.quagent/skills` へ安全にコピーします（合計 16 MiB 上限、通常ファイルとディレクトリのみ）。共有マウントは行わず単方向コピーであるため、VM 側からホスト側のスキルが書き換えられることはありません。VM 内では各エージェントのスキルディレクトリへシンボリックリンクが展開されます。実体が `~/.quagent/skills` に配置されるため、後述の設定ファイル不可視化の制約を受けず、エージェント本体およびサブプロセスの両方から安全に参照できます。

## 接続先申請の内部構造: 自前 DNS と透過プロキシで許可ドメインのみを動的に通す

接続の可否は DNS レベルで判定します。子 netns 内の自前 DNS サーバーは、許可ドメイン（完全一致または `*.example.com`）宛ての問い合わせのみを上流へ転送し、解決先 IP アドレスのみを nftables で動的に通過許可します。許可対象は HTTP/HTTPS（TCP 80/443）のみであり、他のポートへの新規接続はできません。

未許可ドメインは名前解決できず、外部 DNS サーバーへの直接通信も遮断されるため、DNS トンネリング等による情報持ち出しを防ぎます。なお、DNS 応答に含まれる CNAME の遷移先ドメインは許可リストに自動追加されません（その応答で得られた IP アドレスのみ一時的に通過します）。

また、許可ドメインであっても、解決先 IP が内部向けアドレス（プライベート LAN、ループバック、クラウド事業者のメタデータ等のリンクローカル、Tailscale 等の CGNAT）の場合は通信を遮断します。これは、DNS 応答の改ざんによる内部ネットワークへの不正アクセスを防止するためです。拒否ログは承認コンソールに表示されます。

許可された IP 宛ての通信は、子 netns 内の透過プロキシを経由します。プロキシは接続開始時のパケットからホスト名（TLS の SNI、HTTP の Host ヘッダー）を読み取り、事前に許可されたドメイン名と一致しない場合は即座に接続を切断します。nftables の許可は IP 単位であるため、透過プロキシを挟むことで、同一 IP を共有する別ホストや共有 CDN への意図しない接続リスクを排除します。SNI や Host ヘッダーが存在しない、または解析できない接続も安全側に倒して切断されます。なお、この段階では TLS 終端を行わないため通信内容の閲覧は行いません。

## VM 内部の多層防御: seccomp・Landlock・PID 検証でサブプロセスの権限を奪う

ホスト側の境界防御に加えて、VM 内部の実行コマンドにもエージェント自身では解除できない制限を適用します。ポリシーはホスト側から cloud-init 経由で `/etc/quagent/sandbox.json`（root 所有、パーミッション 0644）に配置されます。VM 内の受信デーモン（`quagent-guest`）は、すべてのコマンドをサンドボックス起動プロセス（`quagent-guest __sandbox`）経由で実行します。

起動プロセスは `no_new_privs` フラグを設定した上で seccomp および Landlock を適用し、本来のコマンドへ `exec` します。一度適用された制限は昇格・解除できず、すべての子プロセスへ継承されます。VM 内部の作業ユーザーは非 root であるため、エージェントが自力で制限を解除することはできません。

### 1. seccomp による危険システムコールの拒否
- **compat モード (既定):** `bpf`、カーネルモジュール操作 (`init_module` 等)、`kexec`、`reboot`、`ptrace`、`userfaultfd`、カーネル鍵操作 (`add_key` 等)、`name_to_handle_at`、`open_by_handle_at` を EPERM で拒否します。さらに `socket(AF_VSOCK)` の作成を遮断し、VM 内部からホスト側 vsock ポートへの直接接続やポートスキャンを防止します（`deny_vsock: false` で無効化可能）。
- **strict モード:** compat に加え、`mount`、`umount2`、`unshare`、`setns`、`chroot`、`pivot_root`、`io_uring`、`perf_event_open`、`process_vm_readv` などを拒否します。エージェント自身が直接コンテナ隔離ツールや `io_uring` を使用するタスクは制限されます。
- **ABI 詐称の防止:** 異なる ABI からの同一番号システムコール（32bit の `int 0x80`、x32 など）は拒否され、プロセスは強制終了されます。64bit 以外のバイナリは実行できません。

### 2. Landlock によるファイルシステム書き込み制限 (`landlock: true`、既定: 無効)
ファイルやディレクトリの変更（書き込み・作成・削除・リネーム）を `read_write_paths`（既定: ホームディレクトリ、`/work`、`/tmp`、`/var/tmp`、`/run/user/<uid>`、`/dev/shm`）配下に限定します。読み取り操作は制限されません。タイポ等による事故を防ぐため、指定パスが存在しない場合は起動時にエラーを返します。

### 3. プロセス間権限分離 (窓口アクセスの接続元 PID 検証)
ホスト窓口 (`quagent.host:7070`) への中継デーモンは、TCP 接続の受付時に `/proc/net/tcp` と `/proc/<pid>/fd` から接続元 PID を特定し、プロセスツリーを検査します。窓口への接続を許可するのはエージェント本体プロセスのみです。テストコードやビルドスクリプトなどの子孫プロセスからの接続は即座に遮断されます。万一設定ファイルの認証トークンが漏洩した場合でも、サブプロセスから直接 MCP ツールや LLM API を不正利用される心配はありません。

### 4. エージェント設定ファイルの不可視化 (`mask_agent_config: true`、既定: 有効)
子孫プロセス（テストコード、ビルドツール、シェル等）に対し、ファイルシステム名前空間（`__subbox`）を用いてホームディレクトリ配下の機密設定パスを不可視化します。対象パス（`~/.config/opencode`、`~/.claude`、`~/.claude.json`、`~/.gemini`、`~/.codex`、`~/.config/quagent`）には空の tmpfs または `/dev/null` を被せます。エージェント本体は正常に読み取れますが、サブプロセスからはファイル自体が存在しないように見えます。なお、コミット署名用の使い捨て鍵（`~/.ssh`）は署名処理に必要なため不可視化の対象外です。

### 5. rootless Docker へのサンドボックス制約継承 (`docker_inherit: true`、既定: 有効)
rootless Docker コンテナに対しても、`sandbox.Policy` に基づく seccomp フィルタ（AF_VSOCK 遮断、危険システムコール拒否、64bit ABI 限定）を反映した Docker 既定プロファイルを透過適用します。コンテナのボリュームマウントを経由した機密ディレクトリの持ち出しも遮断します。

```json
"sandbox": {
  "enabled": true,
  "mode": "compat",
  "deny_vsock": true,
  "landlock": false,
  "mask_agent_config": true,
  "docker_inherit": true
}
```

この仕組みはホスト側の境界制御を代替するものではなく、VM 内部における攻撃面を最小化するための追加レイヤーです。作業に必要なシステムコールが遮断されてしまう場合は、`"enabled": false` で無効化できます。

## 暴走エージェント対策: 全インターフェースに上限を設けてホスト資源枯渇を防ぐ

VM 内のエージェントがホストのリソースや人間の承認者を過剰に消費（枯渇）させないよう、各インターフェースに上限を設定しています。

### ホストリソースの防衛と監視
- **ディスクとログの動的監視:** 起動前にホスト作業ディレクトリの空き容量を検査し、最低空き容量（既定 10 GiB）未満の場合は起動を拒否します。実行中はホスト側で動的監視を行い、ゲスト仮想ディスク（40 GiB）の使用率が 80% に達した際に承認コンソールへ警告を発します。95% 到達時、またはホスト全体の空き容量が安全下限（2 GiB）を切った際には、ACPI 安全停止（SIGTERM）を実行してファイルシステム破損やホスト巻き込みを防ぎます。
- **ログの切詰と cgroups:** `console.log` が上限（50 MiB）を超えた場合は古いログを安全に切り詰めます。利用可能な環境では `systemd-run --user` により cgroups v2（CPUQuota、MemoryMax、TasksMax）を適用します。
- **QEMU のサンドボックス:** ホスト上の QEMU に対しても、cBPF seccomp（31種拒否）、Landlock、ホーム tmpfs 化、FD 上限（2048）、プロセス数上限（512）、nice 10 / OOM スコア 500 を適用し、万が一 VM エスケープが発生してもホストの応答性を守ります。

### 通信と承認インターフェースの上限
- **接続先の申請:** 未承認の申請は最大 1 件のみ保持されます。拒否またはタイムアウトしたドメインは 10 分間再申請できません。1 回の申請あたり最大 20 ドメイン、理由は最大 1000 文字です。
- **承認コンソール:** タブ付き TUI（「承認待ち」「ログ」「履歴」）により、ストリーミングログと承認確認を分離して高い一覧性と操作性を提供します。VM 側から送られる文字列（申請理由、ドメイン名、クリップボード）は、制御文字および Bidi 文字を `\u` 表記にエスケープして画面偽装を防ぎます。通信送信にはタイムアウトを設け、コンソール滞留時もホスト側プロセスをブロックしません。
- **DNS とプロキシ:** 同時クエリ数は最大 64 件、キャッシュは最大 4096 件です。DNS トンネリング兆候（FQDN 総長 >180、ラベル長 >50、エントロピー >3.8、6階層以上、TXT/ANY クエリ）を検知して即時遮断（REFUSED）します。透過プロキシのヘッダ読込上限は 64 KiB、同時接続数は最大 64 本です。
- **PR とコマンド実行:** PR タイトルは最大 256 文字、本文は最大 60000 バイト、1 PR あたり最大 500 コミット、PR 作成間隔は 10 秒以上を要求します。コマンド出力は最大 1 MiB、実行タイムアウトは 10 分です。
- **サービス窓口 (LLM/MCP):** run ごとの一時トークンを要求し、該当 VM 以外の接続は即座に切断してホスト監査ログ (`host.log`) に記録します。同時接続数は最大 64 本です。

> **【運用前提】外部 LLM API の課金クォータ:**
> 現時点では、外部 LLM API の利用量（課金コスト）に対するクォータ制限は設けていません。API キー発行元のダッシュボード等で上限を設定してください。

## LLM API の認証プロキシ: 一時トークンで中継し本物の API キーを VM に渡さない

ホスト側のサービス窓口（LLM プロキシおよび MCP サーバー）は、run ごとに生成される一時認証トークンを要求します。

トークンはエージェントの設定ファイル（パーミッション 0600）にのみ書き込まれます。ゲスト内のサービス中継（`quagent-guest`）が接続元プロセスの PID を検証し、エージェント本体以外のサブプロセスからの窓口接続を遮断します。そのため、エージェントが実行したテストやビルドプロセスからサービスを不正利用することはできません。VM 内の Docker コンテナもホスト側サービスへの通信経路自体を持ちません。

API キー等の認証情報は VM 内には配置しません。VM 内のエージェントは `http://quagent.host:7070/llm/<provider>` を baseURL として利用し、ホスト側のプロキシが正規の API キーを付与して本来の API エンドポイントへ転送します。VM からは上流 API のドメインへ直接アクセスできません（既定のアウトバウンド通信は遮断されています）。

### プロバイダ別のプロキシ中継仕様

- **opencode:** `http://quagent.host:7070/llm/<provider>` 経由で上流へ中継します。プロキシが `secret_command` 等で取得したキーを付与します。OpenCode の API キーは Zen（Free モデルを含む全モデル）と Go（サブスクリプション）で共通であるため、`providers` に `opencode-go` または `opencode` のいずれかを設定すると、ホスト側がもう片方のエンドポイント（Zen: `https://opencode.ai/zen/v1`、Go: `https://opencode.ai/zen/go/v1`）を同一のキーで自動補完し、両方の中継ルート（`/llm/opencode` および `/llm/opencode-go`、ならびに `/zen` および `/zen/go` エイリアス）を登録します。ゲスト側では OpenCode v2 形式（`providers.<id>.settings.baseURL`）および v1 形式（`provider.<id>.options.baseURL`）の設定を生成し、VM 内から Go サブスクモデルと Zen Free モデルをシームレスに切り替えて利用できます。
- **Claude Code:** `ANTHROPIC_BASE_URL` をプロキシに向け、API キーの代わりに認証トークンを `apiKeyHelper` 経由で渡します。サブスクリプション（Pro/Max）利用時は、ホスト側で `claude setup-token` により生成した長期トークンをホスト側のみに保持し、VM 内には一時トークンのみを渡します。なお、`setup-token` は推論専用のため、VM 内の `/usage` は使用できません（ホスト側の Claude Code で確認します）。
- **agy (Antigravity CLI):** API キー利用時は `GOOGLE_GEMINI_BASE_URL` をプロキシに向け、認証トークンを `GEMINI_API_KEY` として渡します。
- **codex (Codex CLI):** API キー利用時は `OPENAI_BASE_URL` をプロキシに向け、認証トークンを `OPENAI_API_KEY` として渡します。サブスクリプション（ChatGPT Plus / Pro 等）利用時は、ホスト側の OAuth ログイン情報から短命トークンを生成してプロキシが付与します。

### agy サブスクリプション利用時の内部制御

ホスト側でログイン済みのサブスクリプションを利用する場合、ホスト側が OAuth ログイン情報から短命トークンを再生成してリクエストに付与します。

- **通信の特例 (一時的な Egress 開放と TLS 素通し):**
  起動直後のユーザー情報確認とプロフィール画像取得はゲストから直接アクセスされるため、その宛先（`www.googleapis.com` および画像ホスト）宛てのみ、`--agent agy` 指定時に一時的に egress を開放します。初回推論が通過した時点で即座に遮断します。この通信は `header_policy` 有効時も TLS 終端せず素通しします（終端すると Authorization ヘッダが落とされて 401 となり、起動できないためです）。
- **リフレッシュトークンの取得元:**
  長期の `refresh_token` は、既定でホストのトークンファイル (`~/.gemini/antigravity-cli/antigravity-oauth-token`) から読み込みます。secret-service（キーリング）や `pass` で別管理している場合は、`agy` の `refresh_token_env`、`refresh_token_file`、`refresh_token_command` で指定します（JSON または素の文字列に対応。secret-service の場合は `["secret-tool", "lookup", ...]` を指定）。
- **起動前の認証事前検証:**
  サブスクで agy を起動する前（および再起動で agy を選び直した際）は、ホスト側で `agy models` を短時間実行して認証が通るか確かめます（推論枠は消費せず、プロセスは即座に終了します）。確認に失敗した場合、初回起動時は VM を作成せずに終了し、再起動時は VM を残したまま選び直し画面へ戻ります。

### codex サブスクリプション利用時の内部制御

ホスト側でログイン済みのサブスクリプションを利用する場合、ホスト側が OAuth ログイン情報から短命トークンを再生成してリクエストに付与します。

- **通信の特例 (一時的な Egress 開放と TLS 素通し):**
  起動直後の通信のため、宛先（`chatgpt.com`, `auth.openai.com`）宛てのみ、`--agent codex` 指定時に一時的に egress を開放します。初回推論が通過した時点で即座に遮断します。この通信は `header_policy` 有効時も TLS 終端せず素通しします。
- **リフレッシュトークンの取得元:**
  既定でホストのトークンファイル (`~/.codex/auth.json`) から読み込みます。secret-service（キーリング）や `pass` で別管理している場合は、`codex` の `refresh_token_env`、`refresh_token_file`、`refresh_token_command` で指定します。
- **起動前の認証事前検証:**
  サブスクで codex を起動する前（および再起動で codex を選び直した際）は、ホスト側で `codex --version` を短時間実行して確認します。確認に失敗した場合、初回起動時は VM を作成せずに終了し、再起動時は VM を残したまま選び直し画面へ戻ります。

### 転送対象エンドポイントの制限

認証プロキシがトークンを付与して転送するのは、推論およびモデル一覧取得の操作に限定されます。

- **許可エンドポイント:** `POST /messages`、`/messages/count_tokens`、`/chat/completions`、`/responses`、`/models/*`、`GET /models`、およびそれぞれの `/v1`、`/v1beta` プレフィックス付きパス。
- **拒否エンドポイント:** ファイルアップロードやバッチ API など、その他のエンドポイントへのアクセスは HTTP 403 で拒否され、承認コンソールに通知されます。
- **許可リストの追加:** provider ごとに `"allow": ["POST /messages", "GET /models/*"]` のように明示指定することで、既定リストを上書き・カスタマイズできます。

## ツールサーバー: OpenAPI 仕様から MCP ツールを自動生成してプロキシする

設定の `tool_servers` に指定された OpenAPI サーバー（Open WebUI のツールサーバーなど）は、ホスト側で MCP ツールに変換され、組み込みツール群と並んで登録されます（`internal/toolserver`）。

- **仕様取得と変換:** VM 起動時にホストが OpenAPI 3.x 仕様を取得し、各 operation を個別の MCP ツールとして構築します。ツール名は `<設定キー>__<operationId>` です（operationId 未定義時は HTTP メソッドとパスから自動生成し、最大 64 文字に制限）。スキーマ内の `$ref` 参照はインライン展開し、循環参照は自動で打ち切ります。
- **引数とリクエスト構築:** パス・クエリ・ヘッダー引数は同名のツール引数となり、リクエストボディは `body` 引数に割り当てられます。ボディ形式は JSON を優先します。
- **プロキシ転送:** エージェントによる呼び出しは、ホスト側ネットワークからツールサーバーへ直接 HTTP リクエストとして転送されます。そのため、VM 内の egress 制限やプライベート IP 遮断ルールの影響を受けません。なお、意図しない宛先変更による認証情報漏洩を防ぐため、リダイレクトには追従しません。
- **認証と機密情報の保護:** `secret_env`、`secret_file`、`secret_command` のいずれかが設定されている場合のみ、ホストが転送直前に正規の認証ヘッダーを付与します。エージェント側から指定された `Authorization` や `Cookie` 引数は無視され、機密情報が VM 内に渡ることはありません。
- **レスポンス処理:** レスポンス本文は最大 1 MiB までテキスト形式でエージェントへ返却され、超過分は切り詰められます。バイナリデータ等についてはデータサイズのみを通知します。HTTP 2xx 以外はツール実行エラーとして扱います。

> **【脅威モデル】ツールサーバーの信頼境界:**
> ツールサーバーおよびその OpenAPI 仕様は、ユーザーが信頼して設定したものとして扱われます。ツールの説明文やスキーマ定義はそのままエージェントのプロンプト文脈に注入されるため、悪意あるサードパーティ製サーバーを登録した場合はプロンプトインジェクションの侵入経路となり得ます。信頼できるサーバーのみを登録してください。

## ヘッダの制限 (header_policy): 動的 CA による決定論的 TLS 終端と不要ヘッダの除去

許可済みドメイン宛ての通信であっても、ヘッダ（User-Agent への機密埋め込み、Cookie、独自ヘッダ等）やリクエストボディは持ち出しの経路になります。`header_policy` を有効にすると、VM から外へ出る HTTP リクエストのヘッダを絞り、User-Agent を固定します（既定: 無効）。

```json
"header_policy": {
  "enabled": true,
  "user_agent": "quagent",
  "allow": ["Accept-Language"],
  "deny_request_body": true,
  "allowed_methods": ["GET", "HEAD"],
  "passthrough_https": ["*.pinned.example"],
  "hosts": {
    "*.example.com": { "allow": ["X-Example-*"] },
    "registry.example.org": { "allow_request_body": true, "allowed_methods": ["POST", "PUT"] }
  }
}
```

### 1. 通過ヘッダの制限と構文バリデーション
- **通過を認めるヘッダ:** `Accept`、`Accept-Encoding`、`Content-Length`、`Content-Type`、`Range`、`If-Modified-Since` のみです。Cookie、Referer、Authorization、独自の `X-*` などは転送前に除去します。
- **構文検証:** 残すヘッダに対しても値の厳格な検証を行います（RFC 1123 日時形式、数字のみの Content-Length、制御文字混入防止等）。不正な値や余計なパラメータが埋め込まれたヘッダは落とされます。
- **User-Agent 固定:** 常に指定値（既定 `quagent`）で置き換えます。
- **ボディとメソッドの制限:** `deny_request_body: true` を指定すると、リクエストボディを持つ通信を HTTP 400 で遮断します。`allowed_methods` により許可メソッドを制限できます。

### 2. 決定論的 TLS 終端 (動的使い捨て CA)
HTTPS のヘッダを検査・除去するため、ホスト側で使い捨て CA による TLS 終端（MITM）を行います。

- **証明書の検証:** 許可宛先への通信をホスト側で TLS 終端し、ヘッダを絞った後、本来の宛先サーバーへ TLS 接続を再確立して転送します。再接続時も上流サーバーの証明書はシステムのルート証明書ストアで検証されるため、セキュリティ検証が緩むことはありません。HTTP/2 受信時も適切にストリームごとにヘッダを絞り、上流へ中継します。
- **証明書ピニング対応 (`passthrough_https`):** 証明書ピニングを行うクライアントは動的 CA を拒否するため通信できません。対象ホストを `passthrough_https` に指定することで、その宛先のみ TLS 終端を行わずに透過させることが可能です（SNI / Host ヘッダーの検証は継続されます）。
- **適用範囲と制約:** 透過プロキシで TLS 終端した HTTPS、平文 HTTP、およびツールサーバー経由の呼び出しが対象です。**LLM 認証プロキシは対象外**です（プロバイダ固有のヘッダを保つため）。上流サーバーが HTTP/2 に対応していない場合は通信を中継できません（HTTP/1.1 への自動フォールバックは行いません）。また、HTTP/3 (QUIC / UDP) は透過プロキシの対象外です。

### 3. 宛先別の静的緩和と動的申請 (MCP)
- **静的緩和 (`hosts` / `allow`):** 特定宛先でのヘッダ追加、User-Agent 維持 (`keep_user_agent`)、ボディ許可 (`allow_request_body`)、メソッド緩和を指定できます。
- **動的申請 (MCP):** エージェントは MCP の `request_header_relaxation` を通じて動的に緩和を申請できます。承認コンソール上で対話的に許可し、不要になった緩和は `release_header_relaxation` で解放できます。

## データ持ち出し防止: パターン検査 (DLP) と DNS トンネリング検知で外部密輸を阻止する

quagent は VM から外部への意図しない機密情報持ち出しや、不正な外部通信チャネルの確立を多層で防止します。

### 1. コンテンツ検査エンジン (Content Guard / DLP)
Web 透過プロキシを通過するすべての HTTP リクエスト（URL、ヘッダ、リクエストボディ）を透過的かつ決定論的に走査し、機密情報のパターンを検出します。

- **検査対象パターン:**
  - **秘密鍵:** RSA、EC、DSA、OPENSSH の PRIVATE KEY ブロック
  - **クラウド認証情報:** AWS アクセスキー (`AKIA...`)、Google API キー (`AIza...`)
  - **開発プラットフォーム:** GitHub Personal Access Token (`ghp_...`、`gho_...` 等)
  - **チャット・SaaS トークン:** Slack トークン (`xox[baprs]-...`)
  - **LLM API キー:** OpenAI/LLM API キー (`sk-...`)
  - **トークン・認証ヘッダ:** JSON Web Token (JWT)
- **検知時の遮断動作:** 機密情報が検知された場合、上流サーバーへは転送せず即座に HTTP 403 Forbidden（JSON レスポンス）で遮断し、承認コンソールおよび `host.log` に遮断イベントを通知します。
- **設定:** `config.json` の `content_guard`（既定で有効、`"enabled": false` で無効化可能）により制御されます。

### 2. DNS トンネリング検知
許可済みドメイン配下の不正なサブドメインを用いた DNS トンネリング攻撃（FQDN ラベルへのデータエンコードによる外部密輸）を阻止するため、自前 DNS リゾルバにおいて以下をリアルタイム監視します。

- **検知基準:**
  - FQDN 総長: 180 文字超
  - 単一ラベル長: 50 文字超
  - シャノンエントロピー: ラベルのエントロピーが 3.8 超（Base64/Hex エンコードされた高エントロピー文字列の検出）
  - 深層サブドメイン: 6 階層以上の深層ドメイン
  - 不審なクエリタイプ: TXT、NULL、ANY 等、データの送受信に悪用されやすいレコードタイプ
- **検知時の動作:** 疑わしいクエリは上流リゾルバへフォワードせず即座に REFUSED 応答で遮断し、承認コンソールに通知します。

## PR 作成とコミット再署名: 一時鍵とホスト正規鍵の連携で安全に公開する

エージェントは `/work` の保護されていないブランチにコミットを作成し、MCP の `create_pull_request` ツールを通じてプルリクエストの作成を依頼します。GitHub のパーソナルアクセストークンやコミット署名鍵は VM 内には配置されません。

### コミット取り込みと再署名の流れ

1. **VM 内での一時署名:** VM 内で作成されたコミットは、run ごとに生成される使い捨て SSH 鍵によって自動的に署名されます。これが「当該 VM 内で生成された正当なコミットである」ことの証明となります。
2. **vsock 経由のブランチ取り込み:** ホスト側が vsock 経由（Git の `ext::` リモートヘルパー）でゲスト OS の `/work` からブランチを取り込みます。run 専用のベアリポジトリを使用し、フックは無効化され、Git オブジェクトはホスト側リポジトリを参照します。また `transfer.fsckObjects=true` により不正・破損した Git オブジェクトの取り込みを遮断します。
3. **ホスト正規鍵によるコミットの再署名:** マージ先ベースブランチと差分を照合し、正当なコミットのみをホスト側の正規鍵で再署名します。
   - **再署名対象:** マージ先ベースブランチに存在しないコミットのうち、一時使い捨て鍵による有効な署名が存在するもののみを対象とします。ホスト側の Git 設定に基づいた正規の署名鍵（対象リポジトリで有効な `gpg.*` / `user.signingkey`、`.git/config` や `includeIf` の設定を含む）で再署名します。
   - **属性の維持:** コミットの内容、コミットログ、author 情報（利用者の名義）は一切変更せず、committer のみ利用者の情報に設定されます。
   - **既存コミットの保護:** ホスト側リポジトリに既に存在するコミット（他者が作成したコミットや未 push のコミット）は、ハッシュ値も署名も変更せずに維持されます。既に push 済みのコミットがゲスト側に残っている場合も内容の一致を確認してそのまま利用します。そのため、同一 PR への追加コミットによって過去のコミットハッシュが改変されることはありません。
   - **拒否条件:** 署名が存在しないコミットや、ホスト側にも存在しない不正なコミット（VM 内で署名を無効化して作成されたものなど）が含まれている場合は処理を拒否します。
4. **GitHub への push と PR 作成:** ホスト側リポジトリの `origin` リモートへブランチを push し、`gh` CLI で GitHub 上に PR を作成します（既に PR が存在する場合はブランチを更新します）。

### 署名鍵と認証情報の隔離

SSH 署名で ssh-agent を利用している場合は、quagent 起動時の環境変数 `SSH_AUTH_SOCK` が参照されます。SSH エージェント転送経由で接続している環境では、転送元のセッションが切断されると以降のコミット署名に失敗します（tmux にアタッチし直しても quagent 本体の実行環境変数は変更されません）。

コミットの author は利用者の名義で作成されます。VM にはホスト側 Git の `user.name` / `user.email` のみが渡され、署名秘密鍵や GitHub 認証トークンは渡されません。

### プッシュ制御と保護ブランチ

- **プッシュ先の固定:** push 先のリモートは `origin` に固定されています。保護されたブランチ（既定: `main` / `master` / `develop`、`config.json` の `pr.protected_branches` でカスタマイズ可能）への直接 push は拒否されます。
- **force push の防止:** リモートに同名ブランチが存在する場合、先端までのコミットがすべてゲスト側のコミットと一致していれば（以前に quagent が push した PR ブランチであれば）追加コミットを正常に push できます。一致しないコミットが含まれている場合は強制上書き（force push）を行わずエラーとします。
- **未 push コミットの混入防止:** VM に同期されるコミットは既定で origin に公開済みのものに限定されるため、ホスト側の未 push コミットが意図せず PR に混入することはありません。`--local-head` を指定した場合は現在チェックアウト中のブランチの未 push コミットも VM に同期され、PR として origin へ公開対象となり得ます（前述の通り、ホスト側の既存コミットは再署名されずそのまま維持されます）。

### 承認フロー (`--pr-approval`)

PR 作成は既定で承認制（`--pr-approval`、TUI の起動設定「PR を承認制にする」が既定有効）です。ホスト側がブランチを取り込んで push する直前に、承認コンソール上でブランチ名、マージ先、タイトル、本文を提示して `y` / `n` の確認を求めます。

- `n` が入力された場合や 10 分間応答がない場合は、push および PR 作成は中止されます。
- 自動 push に戻す場合は `--pr-approval=false` を指定します。
- 承認フローを有効にした場合でも、PR 作成後に GitHub 上で内容を最終確認することを推奨します。

## 環境構築手順のコード化: レシピディレクトリによるベースイメージ管理

各 OS の環境構築手順は `internal/image/recipes/<名前>/` ディレクトリ配下に独立して定義されています（`recipe.json` にクラウドイメージの取得元 URL や検証情報、`user-data.yaml` にビルド用の cloud-init 設定を記述）。レシピを新規追加・修正する際の詳細な仕様や規約については、skill `recipe-authoring` を参照してください。

## 今後の課題とアーキテクチャの展望

現状のアーキテクチャにおいて、さらなる堅牢化や運用の利便性向上のために検討されている主な課題です。

- **Egress 通信の統計・監査レポートの出力強化:** 許可済みドメイン宛ての通信量やプロトコル種別、ブロックされた通信イベント（DLP、DNS トンネリング、未許可接続）のサマリーをセッション終了時にレポートとして出力・永続化する機能。
- **外部 LLM API の利用量・課金クォータ管理:** 現在の LLM 認証プロキシは透過的な認証付与と安全なエンドポイント絞り込みに特化しており、トークン数や利用金額の制限機能は持ちません。エージェントの暴走による課金超過を防ぐための利用枠上限設定やレートリミット機能の追加が検討されています。
- **TLS 終端時の HTTP/1.1 自動フォールバック:** 決定論的 TLS 終端において、上流サーバーが HTTP/2 に対応していない場合は通信を中継できません。HTTP/1.1 への自動フォールバックを安全に実装し、中継可能な宛先の幅を広げる余地があります。
- **DNS over HTTPS (DoH) / TLS (DoT) 迂回の完全遮断:** 通常の 53 番ポートに対する DNS トンネリングは自前リゾルバで遮断していますが、許可済み Web サーバー上で動作する DoH/DoT エンドポイントを利用したトンネリングに対する監視・遮断機構の検討。
